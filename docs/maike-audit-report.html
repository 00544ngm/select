1.1 两个 Maike 槽位

注意：两个槽位使用同一 API Key（加密存储于 provider_configurations.encrypted_api_key，Fernet 加密，密钥文件 backend/.api-config.key）。custom 的连接测试返回「连接成功，发现 17 个模型，默认模型 gpt-5.6 当前不可用（PROVIDER_UPSTREAM_UNAVAILABLE）」，但短结构化探针可验证成功，属上游间歇性。

1.2 请求链路

前端 Workbench → POST /api/v1/jobs → ARQ Worker → ProviderClientResolver → OpenAILLMClient → AsyncOpenAI
base_url=maike-ai.top/v1 → Maike
上游 GPT/Claude

对于 custom 槽位，ProviderClientResolver.resolve_primary() 从数据库读取已验证的 transport_mode 和 structured_output_mode，注入 OpenAILLMClient 构造参数。对于 claude 槽位，走 AnthropicLLMClient（原生 Messages API）。

2.1 模型验证流程

ProviderModelVerifier._verify_custom_openai() 对每个模型依次探测三种结构化模式：

json_schema → json_object → prompt_json → (兜底) responses + prompt_json

当前所有已验证的 custom 模型均命中第一档 json_schema（strict mode），因此 transport_mode = chat_completions、structured_output_mode = json_schema。从未落入 responses 兜底路径。

重试机制：每个模型最多 2 次受控重试（max_retries=1，即 1 次初始 + 1 次重试）。模型轮换：启用时按前端配置的顺序依次尝试，每个模型最多一次。

设计决策：I-211 将 Maike GPT 通道的任务级上限从 600s 放宽到 1000s，ARQ 外层兜底从 600s 提到 1200s。I-212 将 gpt-5.6 家族并入慢速报告名单（单请求 600s）。两项改动后，代码侧已给 Maike 通道最大合理预算，剩余失败属上游容量/稳定性问题，非本软件可调。

7. 建议与后续方向

7.1 当前状态评估

Maike 中转供应商在 短结构化探针 层面完全可用（4 个 gpt 模型 + 1 个 claude haiku 均 verified）。但在 完整报告 层面成功率仅 ~42%，且失败模式高度一致：上游在 4–5 分钟后断开（MODEL_UPSTREAM_UNAVAILABLE）。代码侧可调杠杆已用尽：单请求 600s、任务 1000s、ARQ 外层 1200s。

7.2 短期建议

  1. 保持当前协议不变（chat_completions + json_schema）。Responses API 虽然在端点层面可用，但间歇性更严重，切换无收益。
  2. 考虑将 default_model 从裸 gpt-5.6 改为 gpt-5.6-terra（当前使用最多、成功率最高的模型）。避免新任务不带 model 时被拦截。
  3. 保持模型轮换开启。当前 terra → sol → 5.5 → haiku 的轮换顺序合理，失败时自动切换。
  4. Maike 作为辅助通道，正式报告优先使用 OpenAI 官方或 DeepSeek。Maike 仅在轮换时作为备选。

7.3 长期方向

  1. 请求瘦身：缩小 HypothesisOutput schema 尺寸（I-212 所述 A 方向），虽然 I-213 证明 schema 形态不是瓶颈，但减小输出 token 量可能降低上游断开概率。
  2. 供应商侧确认：Maike 若确为「长生成/大输出」上游限制，需联系供应商确认生成 token 上限、时长上限或渠道负载策略。
  3. 分流策略：短验证走 Maike（低成本），长报告走 OpenAI 官方（稳定）。
