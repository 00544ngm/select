# V2.1 运行与结果可信度设计

## 背景

任务 `719ad217-df31-4202-b0f5-340d4ddd2cf3` 在页面显示为“任务已完成”，但实际由未重启的旧常驻进程执行，返回 `combination_model_v2.0`、零个辅品方向和空白的“辅品方向”工作表。

该案例暴露的不是评分权重问题，而是三类可靠性问题：

1. API、Worker 与模型输出之间没有版本握手，旧 Worker 可以继续执行新任务。
2. 候选方向的模型版本仍被硬编码成 V2.0，结果层可能误解真实契约。
3. “程序没有抛异常”和“生成了可用于选品的结果”被混为同一状态。

## 目标

- 新建任务必须由与 API 契约一致的 V2.1 Worker 执行。
- 顶层结果、每个候选、页面和 Excel 必须报告同一个真实模型版本。
- 零候选是允许的专业结论，但必须明确说明原因，不能导出空白报告。
- 首次返回零候选时执行一次受控遗漏复核，不降低门槛、不强制凑数。
- 页面、API、Excel 和运行健康检查形成可审计闭环。
- 保留 V2.0 历史快照，不重算、不覆盖、不伪造 V2.1 字段。

## 非目标

- 不调整 V2.1 六维评分权重、门槛或排序。
- 不修改商品数据库、关键词数据库、采集器或利润模块。
- 不改变 OpenAI-compatible 或 Anthropic-compatible 供应商协议。
- 不把 CatToken 上游 503 当作本轮应用代码问题处理。
- 不为零候选强制生成低粘性商品。

## 方案选择

采用完整可靠性闭环方案：版本握手、结果质量状态、一次遗漏复核、页面与 Excel 明示、项目专用重启验收。

未采用仅重启服务的最小方案，因为它不能阻止未来再次出现旧 Worker 和空结果普通完成态。未采用完整部署平台改造，因为当前是单机应用，新增容器编排或发布系统超出必要范围。

## 一、版本契约与运行握手

### 1.1 唯一契约常量

新增单一业务契约常量：

```text
EXPECTED_COMBINATION_MODEL_VERSION = combination_model_v2.1
```

API 创建假设分析任务时，将以下只读元数据写入任务请求载荷：

- `expected_model_version`：固定为 `combination_model_v2.1`。
- `requested_at_revision`：当前 Git 提交号；无法读取 Git 时使用构建环境提供的 revision，否则为 `unknown`。

这些字段只用于运行审计，不传给供应商，不包含任何密钥。

### 1.2 Worker 执行前校验

Worker 领取任务后、调用采集器或供应商之前执行契约校验：

- `expected_model_version` 与 Worker 常量一致：继续。
- 不一致：任务失败，错误码为 `MODEL_CONTRACT_MISMATCH`，错误不可重试，错误信息明确要求重启 Worker。
- 历史任务缺少该字段：按历史兼容路径运行，不补写或伪造版本。

### 1.3 模型输出校验

V2.1 新任务只接受顶层 `model_version=combination_model_v2.1`。供应商若返回 V2.0 或缺少版本，结构化解析后立即失败，错误码为 `MODEL_CONTRACT_MISMATCH`。

每个 `HypothesisDTO.model_version` 必须继承已经校验的顶层版本，禁止硬编码。序列化阶段再次断言候选版本全部与顶层一致；不一致则不保存“完成”结果。

### 1.4 健康检查

Worker 启动时向 Redis 写入运行身份记录，至少包含：

- `model_version`
- `revision`
- `started_at`
- `worker_id`

记录设置有限 TTL，并由 Worker 心跳刷新。`/api/v1/health/ready` 增加：

- `api_model_version`
- `worker_model_version`
- `api_revision`
- `worker_revision`
- `contract_match`

只有数据库、Redis、Worker 存活且模型版本一致时，`contract_match` 才为 `ok`。revision 为 `unknown` 时不阻断本地运行，但健康响应必须如实展示；已知且不一致时 readiness 返回不一致状态。

## 二、运行状态与业务结果状态分离

数据库任务状态继续使用：

- `queued`
- `running`
- `completed`
- `failed`

不新增数据库迁移。业务结果在 `result_payload.result_status` 中表达：

```text
completed_with_qualified_candidates
completed_needs_evidence
completed_no_qualified_candidates
```

判定矩阵：

| 条件 | 数据库任务状态 | result_status | 是否可直接进入采购测试 |
| --- | --- | --- | --- |
| 至少一个 `execution_status=pass` | completed | completed_with_qualified_candidates | 仅按候选最终动作判断 |
| 无 pass，但至少一个 hold | completed | completed_needs_evidence | 否，先补证据 |
| 无 pass、无 hold，只有 reject 或零方向 | completed | completed_no_qualified_candidates | 否 |
| 契约错误、供应商错误、结构损坏 | failed | 无完成结果 | 否 |

结果载荷同时保存：

- `raw_direction_count`：模型返回方向数。
- `qualified_direction_count`：pass 数。
- `hold_direction_count`：hold 数。
- `rejected_direction_count`：reject 数。
- `rejection_summary`：按拒绝码聚合的数量。
- `result_message`：面向用户的明确结论。

“任务完成”只代表分析流程完成；页面必须同时展示业务结果状态，不能只显示数据库状态。

## 三、零候选受控遗漏复核

### 3.1 触发条件

只在第一次 V2.1 结构化输出满足 `directions=[]` 时触发一次遗漏复核。以下情况不触发：

- 已返回方向，但全部被服务器 gate 拒绝。
- 有 hold 候选。
- 供应商、采集或结构化解析失败。
- 历史 V2.0 任务。

### 3.2 复核内容

第二次请求复用同一主品事实，并明确告知第一次返回零候选。它只检查是否遗漏以下生命周期入口：

- 安装与规格兼容
- 使用中的必要依赖
- 非食品耗材与补充
- 保护与维护
- 明确增效
- 专用收纳与运输
- 无需教育的自然联购

复核仍使用完全相同的 V2.1 schema、食品过滤、购买方向和服务器 gate，不降低任何分数或证据门槛。

### 3.3 复核审计字段

结果保存：

- `audit_performed`
- `audit_reason`
- `initial_raw_direction_count`
- `audit_raw_direction_count`
- `audit_outcome`：`recovered_candidates` 或 `confirmed_no_candidates`

最多复核一次。第二次仍为空时，正式输出“未发现合格候选”，不继续调用模型。

## 四、结果质量门槛

任务调用 `repository.complete` 前必须通过质量验证器：

1. 新任务顶层版本为 V2.1。
2. 所有候选版本与顶层一致。
3. `directions_count` 等于结构化方向数量。
4. 每个候选具有购买方向、产品类型、六维评分、证据等级、执行状态和最终动作。
5. `pass` 候选不能是 `reverse_dependency`、`none`、`weak_context`、食品或主品已包含项。
6. 零候选结果具有遗漏复核记录和明确结果消息。
7. 统计数量之和等于结构化方向数量。

质量验证器只校验完整性和服务器规则，不重新解释 AI 商业判断。

## 五、页面设计

### 5.1 固定结果摘要

任务详情顶部在现有主品信息下显示：

- 模型契约
- 供应商与实际模型
- 业务结果状态
- 分析时间与任务 ID
- 合格、待证据、已淘汰数量

### 5.2 无合格候选

不再显示“历史结果暂无结构化方向”作为新 V2.1 结果的通用提示。

V2.1 零合格候选显示：

> 分析已完成，未发现达到高粘性门槛的辅品。本结果不是系统故障，也不建议为了凑数量强行组合。

其下展示遗漏复核结果和淘汰原因汇总。若是旧 V2.0 历史数据，继续显示“历史 V2.0 快照，未保存结构化方向”，避免把历史缺字段解释成新结论。

### 5.3 待补证据

当只有 hold 候选时，页面显示“发现潜在方向，但当前不可执行”，并列出缺失的兼容、安全或商品类型证据。

## 六、Excel 与 API

### 6.1 Excel

新增“结果摘要”工作表，包含：

- 结果状态
- 模型版本
- 供应商与模型
- 初次候选数
- 复核候选数
- 合格/待证据/淘汰数量
- 淘汰原因汇总
- 是否可用于采购决策

“辅品方向”工作表在零方向时仍写入表头和一行状态记录，禁止生成视觉上完全空白的工作表。该状态行不伪装成候选商品。

### 6.2 API

Job detail 与导出 JSON 透传全部状态和审计字段。历史 V2.0 payload 缺少新字段时，前端按兼容默认值显示，不回写数据库。

## 七、项目专用重启与验收脚本

新增 PowerShell 脚本，严格限制在当前项目绝对路径内：

1. 解析并确认当前项目的 Uvicorn、ARQ Worker 和 Next.js 进程。
2. 只停止命令行与当前项目路径匹配的进程。
3. 校验 `frontend/.next` 位于当前项目后再清理。
4. 按 API、Worker、前端顺序启动，窗口隐藏并记录脱敏日志路径。
5. 等待 `/health/live`、`/health/ready` 和前端页面可用。
6. 断言 `contract_match=ok`、静态资源无 404、模型选择加载完成。

脚本不停止其他项目的 Node/Python 进程，不修改数据库，不输出密钥。

## 八、历史兼容

- 现有 V2.0 任务是只读历史快照。
- 不重新计算、不覆盖分数、不补造方向或证据。
- V2.0 无结构化方向时展示历史兼容提示。
- 只有新建且声明 V2.1 契约的任务适用版本握手、遗漏复核和新结果状态。

## 九、测试策略

### 单元测试

- 顶层版本正确传递到每个候选。
- V2.0 输出不能通过 V2.1 新任务校验。
- pass/hold/reject 计数和 result_status 矩阵。
- 零方向触发且只触发一次遗漏复核。
- 已有方向但全拒绝时不复核。
- 空结果 Excel 仍有结果摘要和状态行。

### API 与 Worker 测试

- 旧 Worker 拒绝 V2.1 任务并返回 `MODEL_CONTRACT_MISMATCH`。
- Worker 身份心跳及 TTL。
- readiness 展示并校验契约版本。
- 质量验证失败时任务为 failed，不保存伪完成结果。

### 前端测试

- V2.1 有合格候选。
- V2.1 只有 hold。
- V2.1 无合格候选及复核说明。
- V2.0 历史空方向兼容提示。
- 模型、供应商、任务 ID 和数量摘要展示。

### 回归样本

- 打印机 + 对应墨盒：正向高粘性。
- 宠物饮水机 + 适配滤芯：正向高粘性。
- 电动研磨器 + 厨房剪刀：弱关联淘汰。
- 婴儿后视镜 + 婴儿安全座椅：反向依赖淘汰。
- 任意主品 + 食品：过滤。
- 自行车手机前梁包：允许无合格候选；普通车灯、打气筒等仅同骑行场景商品不得为 pass。

## 十、真实验收

自动化通过后执行：

1. 使用项目专用脚本重启全部应用进程。
2. 确认 API 与 Worker 的 V2.1 契约一致。
3. 使用自定义 Anthropic 供应商新建一条真实任务并完成。
4. 对照页面、API、JSON 和 Excel 的版本、方向数、状态、评分和动作。
5. CatToken 仅在最小连接恢复后进行独立真实任务验收；仍为 503 时如实记录为供应商上游不可用。

通过标准：

- 新任务不再产生 V2.0 结果。
- 零候选不会产生空白报告或普通完成误导。
- 页面、API、JSON 与 Excel 一致。
- 自动化回归全部通过。
- 至少一条自定义 Anthropic V2.1 真实任务完成。

## 十一、实施分段与回滚

实施拆分为四个独立提交：

1. 版本契约、候选版本透传和 Worker 握手。
2. 结果状态、质量门槛和一次遗漏复核。
3. 页面、API 与 Excel 展示。
4. 项目专用重启脚本和完整验收记录。

每个提交均先增加失败测试再实现，并在 `docs/优化迭代记录.md` 记录验证结果和失败案例。`dump.rdb` 继续视为用户文件，不删除、不提交。
