# 否决审查与互补需求证据设计

## 目标

把判定 B（审判结果）中的原始布尔字段改造成用户能够直接理解、能够追溯证据的展示，同时保持现有评分、否决结果、模型输出字段和历史任务数据兼容。

本设计采用已经确认的“方案 A”：结论卡 + 分类状态，并将 `g3_validated` 从风险项中移出，作为独立的正向证据展示。

## 不在本次范围内

- 不改变 G1-G7 的业务含义。
- 不改变 C-Score、B-Score、最终等级、优先级分数或否决规则。
- 不改变既有 `g3_validated`、`vetoed`、`veto_reason` 字段的含义。
- 不重算、不覆盖历史任务的原始结果。
- 不将“未验证互补需求”自动解释为否决。

## 当前问题

当前页面直接展示 `True` 和 `False`：

- 风险字段为 `False` 时，用户容易误以为检查失败，实际含义是风险未触发。
- `g3_validated` 是正向证据，却与六个风险字段混在一起。
- 模型只输出 `g3_validated` 布尔值，没有给页面提供命中数量、样本数量、评论原文、翻译、来源链接和判定原因。
- Walmart 最多抓取 30 条评论，但当前判定提示只接收前 8 条；Amazon 通常最多抓取 15 条。现有 `False` 只能代表有限样本内未确认，不能证明市场上不存在需求。

## 页面结构

每个 B 商品使用一块独立的审查区域：

```text
客品：Progressive Paperworks Lettuce Keeper

否决审查                                      [通过]
未触发任何一票否决条件

风险检查
节奏不匹配                                    未触发
竞品冲突                                      未触发
品牌压制                                      未触发
物流问题                                      未触发
法律风险                                      未触发
差评超标                                      未触发

正向证据
互补需求证据                                  暂未确认
当前为有限样本初判，尚无足够的可追溯证据。
```

展示规则：

- `vetoed=false`：绿色“通过”，说明“未触发任何一票否决条件”。
- `vetoed=true`：红色“未通过”，突出显示真实 `veto_reason`。
- G1、G2、G4-G7 的 `false` 显示“未触发”，`true` 显示“已触发”。
- G3 不出现在风险列表，单独显示为“互补需求证据”。
- 未否决时隐藏空白“否决原因”；被否决时显示原因。
- 不直接向用户显示原始 `True`、`False`。

## 互补需求的证据定义

只有 B 商品消费者评论中出现下面任一明确表达，才可算作相关评论：

- 需要与 A 商品同类产品搭配使用；
- 缺少 A 商品提供的功能、附件或使用条件；
- 购买 B 后仍需解决 A 商品对应的问题；
- 明确描述 A 与 B 的组合使用场景。

仅仅因为 A、B 属于相同类目、在相同房间使用或由模型推测可以搭配，不算评论证据。Listing 标题、卖点和描述可以作为辅助判断材料，但不能计入评论命中数量。

## 四级状态

前端展示由证据统计派生，不能由模型自由编写状态名称：

| 状态 | 判定条件 | 用户含义 |
| --- | --- | --- |
| 已验证 | 有效评论不少于 20 条，相关评论不少于 3 条，命中率不低于 10%，并保留至少 2 条明确证据 | 有可复核的消费者需求证据 |
| 有需求线索 | 找到 1-2 条相关评论，但未达到“已验证”门槛 | 存在线索，样本或一致性不足 |
| 暂未发现 | 有效评论不少于 20 条，但没有相关评论 | 当前样本内未发现，不代表需求不存在 |
| 样本不足 | 有效评论少于 10 条，或评论抓取失败、被登录/CAPTCHA/网络拦截 | 不能作出可靠判断 |

有效评论为 10-19 条时：

- 有相关评论则显示“有需求线索”；
- 没有相关评论则显示“样本不足”。

命中率按 `相关评论数 / 有效评论数` 计算。重复评论、空文本、过短且无实际语义的文本不计入有效评论。

## 证据明细

新任务需要为每个 B 商品保存以下结构化信息：

- 数据来源平台和商品链接；
- 验证时间；
- 抓取状态以及失败原因；
- 有效评论数量；
- 相关评论数量；
- 命中比例；
- 四级验证状态；
- 每条命中证据的评论原文；
- 中文翻译；
- 命中的互补需求关键词；
- 与 A 商品形成互补的理由；
- 评论来源链接（平台能够提供时）；
- 证据强度：明确、较强、弱线索。

页面默认显示状态和统计，用户展开后查看证据原文。任何证据都必须来自本次实际抓取的数据；不得由模型补写评论、链接或数量。

## 数据流

1. 商品抓取器采集 B 商品详情和评论，保留平台、商品 URL、抓取状态和实际评论集合。
2. 互补证据分析器对去重后的评论进行结构化判定，返回每条评论是否相关及其理由。
3. 服务端依据固定阈值计算四级状态、命中数量和命中比例。模型不得直接决定最终四级状态。
4. 原有判定流程继续产生 `g3_validated`：只有四级状态为“已验证”时，新任务的兼容字段才为 `true`；其他状态为 `false`。
5. 证据结构作为附加结果保存并通过任务结果 API 返回。
6. 工作台任务详情和历史结果使用同一个展示组件，避免两处含义不一致。

## 模型输出约束

评论分类可以使用当前用户选择的主供应商模型，但必须满足：

- 输入只包含本次实际抓取的评论与 A 商品信息；
- 输出必须逐条对应输入评论，使用稳定的评论索引；
- 不接受模型返回输入中不存在的评论原文；
- 服务端校验评论索引、数量和文本来源；
- 模型输出解析失败时标记“样本不足/分析失败”，不得默认成“暂未发现”；
- 双模型结果可以分别展示或交叉复核，但不能把两个模型重复识别的同一条评论计算两次。

## 历史任务兼容

旧任务通常只有 `g3_validated`，没有证据明细：

- 旧任务 `g3_validated=true` 显示“旧任务初判：已验证”，同时提示“没有保存证据明细，建议重新运行验证”。
- 旧任务 `g3_validated=false` 显示“旧任务初判：暂未确认”，不能显示“暂未发现”。
- 不为旧任务生成评论数量、命中率或证据原文。
- 用户重新运行后，新任务才使用四级状态和完整证据展示。

## 错误处理

- 评论抓取失败、CAPTCHA、登录拦截、页面结构变化：状态显示“样本不足”，展示可理解的失败原因。
- 模型评论分类失败：保留已抓取样本数，状态显示“分析失败”，允许用户重试；不修改原否决审查结果。
- 部分评论分类失败：仅统计成功分类的有效评论，并在页面显示“部分数据未完成分析”。
- 证据结构缺失或格式不合法：按历史兼容方式展示原始初判，不伪造证据。

## 测试与验收

后端测试：

- 四级状态的所有阈值边界：9、10、19、20 条评论，0、1、2、3 条命中和 10% 命中率。
- 评论去重、空文本过滤和命中率计算。
- 模型不得引用不存在的评论索引。
- 抓取失败、分类失败和部分失败的状态。
- 新任务 `g3_validated` 与“已验证”状态保持兼容。
- 既有评分、等级、否决字段和 Excel 导出不发生变化。

前端测试：

- `vetoed=false` 显示“通过”，风险 `false` 显示“未触发”。
- `vetoed=true` 显示“未通过”及真实原因。
- G3 单独出现在“正向证据”，不出现在风险检查。
- 四级状态、统计信息和证据展开内容正确显示。
- 空否决原因不会形成空白行。
- 旧任务显示“旧任务初判”，不显示虚构统计。
- 工作台详情和历史结果显示规则一致。

端到端验收：

- 使用当前自定义 Anthropic 供应商完成一条真实判定 B 任务。
- 核对评论样本数与实际保存数据一致。
- 随机复核至少两条命中证据，确认原文确实来自抓取结果。
- 确认任务结果、历史页面和导出文件中的原有评分与否决结果未被展示改造改变。
