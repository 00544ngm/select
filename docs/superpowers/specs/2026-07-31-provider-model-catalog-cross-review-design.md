# API 模型目录与交叉验证统一设计

## 状态

- 版本：V1
- 日期：2026-07-31
- 设计状态：待用户审阅
- 范围：API 设置、交叉验证模型选择、任务结果与历史记录中的模型身份展示

## 背景与问题

API 设置页当前能够保存供应商、协议、默认模型并显示测试结果，但可用模型只作为表单下拉选项存在，没有形成可追溯的模型身份记录。交叉验证入口仍按 `gpt` / `deepseek` 固定显示和调用，无法反映用户在 API 设置中配置的自定义供应商和实际模型。

因此会出现两类歧义：

1. 页面显示的评审标签与实际请求使用的供应商或模型不一致。
2. 用户无法判断某个模型是否经过真实配置测试，也无法在历史结果中追溯当时使用的模型。

## 目标与非目标

### 目标

- 建立统一的模型目录身份：`provider + api_protocol + model`。
- API 设置页明确展示可用模型、默认模型、测试状态、测试时间和最近错误。
- 交叉验证从已配置且测试通过的模型中自由选择两个不同模型。
- 任务请求、运行状态、结果和历史记录展示实际使用的模型身份。
- 旧任务仍可展示；无法获得完整身份时显示兼容标签，不重算历史结果。
- 失败时在任务状态和页面上明确显示脱敏后的原因。

### 非目标

- 不修改组合评分、推荐排序、阈值或提示词。
- 不修改商品数据库、关键词数据库、采集器或利润计算。
- 不修改 OpenAI/Anthropic 兼容协议。
- 不自动重跑或覆盖历史任务。
- 不持久化 API Key、Cookie 或 Token 到结果载荷、日志或优化记录。

## 方案选择

采用方案 A：统一模型目录。

方案 B（只使用各供应商默认模型）不能满足自由选择和审计要求；方案 C（设置页与交叉验证各自维护模型）会产生配置不同步和测试状态过期问题。方案 A 让所有调用方消费同一份“供应商配置 + 测试结果”数据。

## 模型目录数据契约

现有供应商配置接口继续作为基础来源，扩展公开字段（不包含密钥）：

```text
ProviderModelOption {
  provider: string
  provider_display_name: string
  api_protocol: "openai" | "anthropic"
  model: string
  is_default: boolean
  is_enabled: boolean
  test_status: "success" | "failed" | "untested"
  tested_at: datetime | null
  test_message: string | null
}
```

模型目录只包含已配置供应商返回的模型。只有 `is_enabled = true`、`test_status = success` 的模型可进入交叉验证的可选列表。供应商配置变化后，目录通过现有查询失效机制刷新；不缓存 API Key。

## API 设置页设计

在每个供应商表单的“默认模型”下方增加“模型目录”区域：

- 每个模型显示完整身份：供应商、协议、模型名。
- 默认模型使用“默认”标记；默认选择仍由现有表单保存。
- 显示测试状态和最近测试时间。
- 失败状态显示脱敏错误摘要和“重新测试”操作。
- 模型测试成功后立即显示“可用于交叉验证”。
- 连接参数或模型改变后，清除旧的成功状态并提示必须重新测试。

保存按钮仍遵守现有规则：自定义供应商参数变化后必须先测试成功再保存。已有的供应商标签、API Key 脱敏和协议选择保留。

## 交叉验证选择与数据流

前端交叉验证面板改为从模型目录生成两个选择器：评审模型 A、评审模型 B。每个选项显示：

`供应商显示名 · 协议 · 模型`

提交前必须检查：

1. 两个模型均已选择。
2. 两个模型的 `(provider, model)` 身份不同。
3. 两个模型均启用且最近一次测试成功。

前端提交 JSON：

```text
{
  "reviewer_a": { "provider": "...", "model": "..." },
  "reviewer_b": { "provider": "...", "model": "..." }
}
```

后端再次校验相同规则，不能信任前端状态。队列任务保存脱敏的模型身份快照，以保证配置后来变化时仍能解释本次任务实际选择。

评审结果使用通用键（例如 `reviewer_a`、`reviewer_b`），同时保存每个评审的 `provider`、`api_protocol`、`model`。旧的 `gpt_reviews_deepseek` / `deepseek_reviews_gpt` 仅用于兼容读取，不再作为新任务的唯一协议。

## 结果与历史记录展示

交叉验证结果采用“结论优先”顺序：

1. 总体结论、一致性、评分差和任务状态。
2. 评审模型 A/B 身份卡片（供应商、协议、模型、状态）。
3. 各模型的核心发现与分歧点。
4. 原始评审文本折叠展示。

任务详情和历史列表增加模型身份摘要；长名称允许换行。旧任务若只有 `gpt` / `deepseek` 键，则显示兼容标签；若 payload 没有供应商信息，显示“历史任务未记录模型身份”，不猜测实际模型。

## 状态与错误处理

交叉验证状态至少包括：`queued`、`running`、`completed`、`failed`、`skipped`。状态和脱敏错误写入交叉验证结果载荷，前端停止轮询并显示失败原因及重试入口。

以下情况在提交阶段拒绝：模型未测试、测试失败、供应商禁用、两个模型相同、原任务没有双模型结果。重复提交已有运行中的交叉验证时返回冲突，不重复排队。

错误消息不得包含 API Key、Cookie、Token 或完整请求头；供应商原始异常仅保留安全摘要。

## 兼容与迁移

- 不迁移、不重算旧任务结果。
- 新字段均可选，旧 payload 继续由现有 formatter 展示。
- 结果 formatter 同时支持新通用评审键和旧 GPT/DeepSeek 键。
- 不要求数据库强制迁移；若需要持久化快照，优先复用现有 JSON payload/任务请求字段，避免影响商品和评分表。

## 验证计划

- 后端：模型目录过滤、双模型唯一性、未测试/失败模型拒绝、重复任务冲突、失败状态持久化。
- 前端：API 设置显示模型目录和测试状态；交叉验证选择器显示完整身份；提交前校验；失败/完成状态和旧 payload 兼容展示。
- 类型与构建：前端 typecheck、生产构建、全量前端测试、后端相关测试、`git diff --check`。
- 真实运行：只使用用户已配置的测试通过模型验证一条交叉验证任务；不记录密钥，不覆盖已有历史任务。

## 回滚

实现拆分为独立提交；回退实现提交即可恢复旧的交叉验证入口和显示逻辑，不删除或修改历史任务数据。设计文档本身可保留作为迭代记录。
