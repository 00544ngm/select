# AI 连接自动验证设计

## 目标

将当前依赖手动点击、按页面访问重复触发的模型验证，改为按状态自动触发。正常可用的连接不设置验证有效期，也不因时间经过而重复消耗 Token。

## 已确认行为

1. 保存新的 API 配置，或 API Key、服务地址、接口协议发生变化时，软件自动验证默认模型。
2. 已在当前连接配置下验证成功的模型长期保持可用，不设置 24 小时或其他时间期限。
3. 打开 API 设置页、刷新页面和启动软件都不触发真实模型验证。
4. 正常提交任务时，直接使用已验证模型，不在任务前追加验证请求。
5. 真实任务调用出现模型或连接类失败时，将该次任务调用本身视为失败证据，并触发一次自动短验证以诊断当前连接。
6. 短验证成功时，恢复模型可用状态；任务根据现有重试/模型轮换规则继续处理。
7. 短验证失败时，记录认证失败、模型不存在、限流、上游不可用或网络错误等原因，并按现有模型轮换规则选择下一个候选模型。
8. 抓取、业务门禁、报告没有合格组合等非连接故障不触发验证。
9. 保留手动“重新验证”入口，仅用于主动排障，不再作为日常使用的必要步骤。

## Token 策略

自动短验证保留真实模型请求，以确认 API Key、模型路由和结构化输出路径都能工作。请求内容和输出上限保持很小，因此会消耗少量 Token，但触发频率仅限首次配置、连接配置变化或真实调用失败。

模型目录发现接口本身通常不产生 Token 费用，但不能证明模型可以正常生成报告，因此不作为唯一验证手段。

## 后端设计

### 可用性判断

`ProviderService.is_model_available` 只读取当前连接修订号下的验证记录和勾选状态。验证记录为 `verified` 且连接修订号一致时直接返回可用，不调用模型。

### 保存后自动验证

保存服务商配置后，前端对新增配置或连接参数发生变化的默认模型调用一次自动验证。验证结果写入现有模型验证记录，不引入定时器或过期时间。

### 失败后验证

Worker 在模型调用产生可归因于供应商的技术失败后执行一次短验证，并更新模型验证记录。每个任务、每个失败候选最多触发一次诊断验证，避免失败循环产生额外费用。

原始任务失败仍由现有轮换分类决定是否切换模型，诊断验证不得把业务失败转换为技术失败，也不得降低报告 schema 或质量门。

### 交叉验证

移除交叉验证入口的 24 小时验证期限。只要求模型在当前连接修订号下验证成功，并且仍处于启用/选中状态。

## 前端设计

1. 删除打开设置页时自动复核“已选择模型和最近使用模型”的逻辑。
2. 保存连接配置后显示“正在自动验证”，完成后刷新模型状态。
3. 文案明确说明：验证成功后持续有效；仅在连接配置变化或任务失败时自动复核。
4. 保留手动重新验证按钮，但移除暗示用户必须定期验证的提示。
5. 任务错误文案不再提示“验证已超过 24 小时”。

## 数据兼容

继续使用现有 `validation_revision`、`connection_revision`、`status` 和 `last_auto_tested_at` 字段，不新增数据库迁移。0.1.8 的配置、历史任务和验证记录原样保留。

连接参数变化时已有修订号机制会使旧验证自动失效，随后保存后自动验证新连接；普通软件升级不会使验证失效。

## 测试与验收

1. 已验证且连接未变化时，多次调用可用性检查不会调用模型验证器。
2. 未验证、失败或连接修订号不一致时，不把模型视为可用。
3. 设置页打开和刷新不触发 `verifyProviderModel`。
4. 新配置或连接参数变化保存成功后自动验证默认模型一次。
5. 未变更连接的普通保存不重复验证。
6. 交叉验证接受任意时间验证成功、且连接修订号一致的模型。
7. Worker 仅在供应商技术失败后触发诊断验证，业务失败不触发。
8. 后端、前端、桌面端全量测试、类型检查和生产构建通过后生成 0.1.9 安装包。

## 非目标

- 不增加后台定时验证任务。
- 不在每次任务前探测模型。
- 不取消真实模型短验证。
- 不改变 V2.1 报告结构和质量门。
- 不删除或重置用户现有数据。
