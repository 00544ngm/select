# 全品类非食品组合选品与三态门禁设计

## 1. 目标

软件面向所有常规非食品品类，不针对宠物、家居、汽车或任何单一品类写特殊业务规则。

系统必须同时保证：

1. 主品不能是食品或其他可摄入商品。
2. 辅品不能是食品或其他可摄入商品。
3. 与食品接触但本身不可摄入的商品允许进入分析。
4. 信息不足不能假装为非食品，也不能被误判为确认违规。
5. 普通兼容性、安全性注意事项不能自动变成硬淘汰。
6. 所有最终结论必须可以从结构化状态、理由和来源事实追溯。

## 2. 全局适用范围

允许的常规品类包括但不限于：

- 家居、家具、收纳、清洁工具
- 宠物用品（不含宠物食品及口服补充剂）
- 汽车与摩托车配件
- 消费电子、电脑、手机及配件
- 服装、鞋帽、箱包、珠宝配饰
- 五金、工具、园艺、户外用品
- 玩具、文具、办公用品
- 美妆外用品、个护工具（不可摄入）
- 厨具、餐具、水瓶、饭盒、食品储存容器
- 医疗器械和健康用品（不可摄入且满足其他安全门禁）

全局禁止：

- 食品、零食、糖果
- 饮料、冲调饮品
- 调味品、食材、可食用原料
- 药品及口服药物
- 维生素、口服保健品、膳食补充剂
- 宠物食品、宠物零食、宠物口服补充剂
- 其他设计用途为被人或动物吞咽、饮用或摄入的商品

判断标准是“商品本身是否设计为被摄入”，而不是是否用于食品场景。锅具、水瓶、餐具、宠物食盆属于非食品。

## 3. 核心商品类型

主品和每个辅品统一使用一个服务器裁决字段：

```text
product_type_status:
  non_food    已确认不可摄入，可继续
  ingestible  已确认可摄入，禁止
  unknown     信息不足，暂停核验
```

不再同时维护互相矛盾的 `food_filter_status` 与 `product_type_status`。若为兼容旧数据保留旧字段，它只能由 `product_type_status` 派生，不能独立参与裁决。

## 4. 分类架构

采用“确定性规则优先、结构化模型证据辅助、服务器最终裁决”的三层架构。

### 4.1 确定性规则

规则按语义组合判断，不使用单个宽泛词直接裁决。

示例：

- `water bottle`、`storage container`、`dog bowl` → `non_food`
- `bottled water`、`protein drink`、`dog food` → `ingestible`
- `vitamin organizer` → `non_food`
- `vitamin C tablets` → `ingestible`

规则必须支持否定冲突和短语优先级，避免仅凭 `water`、`food`、`pet` 等单词误判。

### 4.2 模型辅助证据

模型输出：

- 建议类型
- 判断理由
- 支持判断的来源事实 ID
- 不确定点

模型不得直接决定是否放行，也不得用商品类目常识代替缺失事实。

### 4.3 服务器裁决

服务器综合确定性规则和有效来源事实：

- 证据明确为不可摄入 → `non_food`
- 证据明确为可摄入 → `ingestible`
- 证据冲突或不足 → `unknown`

模型与确定性规则冲突时进入 `unknown`，不得自动放行。

## 5. 主品入口规则

主品在生成辅品前完成分类：

- `non_food`：继续商品画像和候选生成。
- `ingestible`：任务停止，状态为“不支持的主品类型”，不调用候选生成模型。
- `unknown`：任务暂停，状态为“主品类型待核验”，列出缺失证据。

主品类型不是评分项，而是产品适用范围门禁。

## 6. 辅品入口规则

每个候选在粘性评分前完成分类：

- `non_food`：进入关系、兼容性、安全性、重复功能和粘性评分。
- `ingestible`：以 `ingestible_blocked` 硬拒绝，不进入评分或推荐排序。
- `unknown`：进入 `hold`，显示“商品类型待核验”，不能进入合格池。

这样可避免高分食品候选绕过范围限制，也避免普通容器因名称模糊被直接淘汰。

## 7. 兼容性、安全性和重复功能三态门禁

三个门禁分别使用：

```text
clear               已确认通过
needs_verification  信息不足或存在可验证条件
blocked             已确认阻断
```

适用规则：

- 任一 `blocked` → `execution_status=reject`
- 没有 blocked，但任一 `needs_verification` → `execution_status=hold`
- 全部 clear → `execution_status=pass`

说明文本不能直接触发门禁。每个 blocked 必须同时具备：

1. 明确状态字段
2. 中文确认理由
3. 至少一个有效来源事实 ID
4. 对应的拒绝码

普通风险、尺寸待确认、材质待确认、成分待确认和安全使用提示均属于 `needs_verification`，除非证据已经确认不可接受。

## 8. 分数与准入分离

V2.1 六维权重和既有阈值保持不变。

- `stickiness_score`：商业关系潜力，0–100。
- `execution_status`：当前是否具备准入条件。
- `decision_action`：下一步业务动作。

高分不能覆盖确认的食品、兼容性或安全阻断；但高分且信息不足应显示“高潜力，待补证据”，不能显示为 0 分或直接淘汰。

对已经确认是 `non_food` 的候选，粘性评分与三态业务门禁独立计算，再由服务器合并结论。因此 `hold` 和 `reject` 也保留真实粘性潜力分；该分数只表达商业关系，不代表已经准入。

业务动作：

- pass 且高分：优先测试或小批量测试
- hold：待补证据后复核
- reject：确认不符合准入条件
- 分数低于最低阈值但无硬阻断：不建议

## 9. 结果质量门禁

结果发布前检查：

1. `ingestible` 候选不得出现在合格或待测试池。
2. `unknown` 候选不得是 pass。
3. reject 必须有 blocked 状态、理由和来源事实。
4. 拒绝码必须与具体门禁一一对应。
5. `product_type_status` 与兼容旧字段不得冲突。
6. 所有候选出现完全相同的多个拒绝码时，标记 `RESULT_QUALITY_INVALID`。
7. 高分候选被拒绝但无确认依据时，标记结果异常。
8. API、JSON、Excel 和页面的状态与数量必须一致。

## 10. 页面设计

每个方向只显示一个主状态：

- 可进入测试
- 待补证据后复核
- 确认不符合准入条件
- 不建议

同时独立显示：

- 粘性潜力分
- 商品类型
- 门禁结论
- 具体理由
- 来源事实
- 下一步需要补充的证据

不再重复显示“拒绝 / 不建议 / 淘汰”三个近似结论，也不再展示无法解释的英文枚举作为主要文案。

## 11. 数据流

```text
抓取主品
  → 主品可摄入分类
    → ingestible：停止
    → unknown：暂停核验
    → non_food：生成辅品候选
      → 辅品可摄入分类
        → ingestible：范围硬拒绝
        → unknown：待核验
        → non_food：并行计算
          → 六维粘性潜力分
          → 三态业务门禁
            → blocked：拒绝但保留潜力分
            → needs_verification：待补证据并保留潜力分
            → clear：可按分数进入业务动作
          → 结果一致性校验
            → API / JSON / Excel / 页面
```

## 12. 历史数据策略

- 历史任务保持只读，不静默重算。
- 旧字段继续支持展示，但标明“旧规则结果”。
- 新规则只应用于新建任务。
- 如需迁移历史任务，必须另立方案并获得明确授权。

## 13. 测试矩阵

### 13.1 主品

- 非食品：家具、手机、汽车配件、宠物背包、服装、工具。
- 可摄入：食品、饮料、药品、维生素、宠物食品。
- 模糊：信息不足或标题只含品牌与型号。

### 13.2 辅品

- 非食品普通配件。
- 与食品接触但不可摄入：锅具、水瓶、饭盒、餐具、宠物食盆。
- 可摄入：调味品、饮料、药片、补充剂、宠物零食。
- 语义对照：`water bottle` 与 `bottled water`、`vitamin organizer` 与 `vitamin tablets`。

### 13.3 门禁

- 尺寸未知 → hold
- 已确认尺寸不兼容 → reject
- 一般安全提示 → hold 或 clear
- 已确认不可接受安全风险 → reject
- 可能重复 → hold
- 已确认主品已包含同功能配件 → reject

### 13.4 跨品类真实验收

至少使用家居、电子、汽车、服装、工具、宠物用品六类非食品主品，各创建真实新任务；另用食品、饮料、口服补充剂和宠物食品验证主品入口拒绝。

## 14. 验收标准

1. 主品和辅品均不能是可摄入商品。
2. 所有常规非食品品类使用同一套规则。
3. 食品接触类非食品商品不会因场景词被误杀。
4. unknown 永远不会进入 pass。
5. 普通说明文本不会生成硬拒绝。
6. reject 均可追溯到状态、理由和来源事实。
7. 页面显示真实 `stickiness_score`。
8. 页面状态简洁且提供下一步动作。
9. 不出现整批候选无依据地带有相同拒绝码。
10. 历史任务不被覆盖。

## 15. 非目标

- 不修改 V2.1 六维权重和既有分数阈值。
- 不为单一商品或单一品类增加硬编码业务特例。
- 不支持食品、药品、保健品或其他可摄入商品选品。
- 不在本次工作中重算历史任务。
