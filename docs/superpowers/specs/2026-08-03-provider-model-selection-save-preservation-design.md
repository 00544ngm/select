# 供应商重复保存保留模型验证与选择状态设计

## 背景与根因

员工电脑首次保存供应商后，前端虽然把服务端返回的供应商写入查询缓存，但没有清空 React Hook Form 中的临时 `apiKey`，`SecretInput` 也继续保持“替换密钥”状态。员工随后验证模型、勾选“使用此模型”并再次点击“保存配置”时，请求会重复携带同一 API Key。后端当前把任何非空 `update.api_key` 都视为密钥变化，并删除该供应商全部模型验证记录，导致刚验证并勾选的模型立即失效。

## 目标

1. 保存成功后，前端不再保留或重复提交明文 API Key。
2. 同一 API Key 被重复提交时，后端不得删除模型验证及勾选状态。
3. API Key、服务地址或协议确实变化时，仍必须使旧模型验证失效。
4. “使用此模型”的勾选继续通过独立选择接口即时保存，不要求用户再次点击“保存配置”。

## 非目标

- 不改变模型验证 24 小时有效期。
- 不改变供应商协议、模型探测或任务预检规则。
- 不迁移或改写历史任务结果。
- 不在日志、测试输出或文档中记录 API Key。

## 方案

### 前端

`ProviderSettingsPanel` 在供应商保存成功后，以服务端返回值重新初始化表单：`apiKey` 设为 `undefined`，地址、协议、名称、启用状态使用已保存值。`SecretInput` 增加与已保存密钥状态同步的重置机制，使界面切回掩码展示，不继续保留明文。

模型勾选成功后继续只更新供应商查询缓存。界面明确提示“模型选择已自动保存”，避免用户误以为还需要点击底部“保存配置”。

### 后端

`ProviderService.save` 在收到新 API Key 且已有加密密钥时，先解密已有密钥并做常量时间比较。只有密钥内容确实变化时，才把它列入 `invalidates_models`；协议或服务地址变化仍按原规则删除验证记录。若旧密钥无法解密，保持安全失败并要求重新录入，不跳过失效处理。

### 数据流

1. 首次保存：持久化加密密钥，前端清空临时明文并展示掩码。
2. 验证模型：保存验证记录。
3. 勾选模型：选择接口即时持久化 `is_selected=true`，前端提示已自动保存。
4. 再次保存未改参数：请求不携带 API Key；即使其他客户端重复携带同一密钥，后端比较后保留验证记录。
5. 替换为不同密钥、修改地址或协议：删除旧验证记录，要求重新发现、验证并勾选模型。

## 错误处理

- 保存失败时不清空表单中的新密钥，允许用户修正后重试。
- 保存成功后才清空临时密钥。
- 同密钥比较不得写入日志或响应。
- 模型选择失败继续显示服务端错误，不伪装为已保存。

## 测试与验收

1. 前端回归：输入新密钥并保存后，第二次保存请求不包含 `api_key`，界面显示掩码。
2. 前端回归：勾选已验证模型后显示“模型选择已自动保存”。
3. 后端回归：重复提交同一密钥不调用 `delete_model_validations`。
4. 后端回归：提交不同密钥、修改地址或协议仍调用 `delete_model_validations`。
5. 真实验收：员工式操作“保存配置 → 测试连接 → 验证 → 勾选 → 再保存”，模型仍保持已验证且已勾选，并能在工作台被选择。

## 回滚

前端与后端改动均不需要数据库迁移。回滚对应代码和测试即可恢复旧行为；不删除用户数据库或历史任务。
